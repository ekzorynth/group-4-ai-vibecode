## การลงมือจริงและการแยกข้อมูล

- เริ่มเตรียมและอ่าน oracle: 2026-11-06 11:10:36 UTC (18:10:36 น. ไทย)
- ใช้ instance `http://127.0.0.1:4343` เท่านั้น ฐานข้อมูลในหน่วยความจำ โหมดปกติ ไม่ได้เรียกพอร์ตผู้ใช้ 4310 และไม่ได้อ่าน runtime source
- เปิด browser/context ของ C3 เอง และเพิ่ม context ที่สองเฉพาะการลองแข่งจองและบัญชีทั่วไป
- รอบเก็บผลครบล่าสุด: **2026-11-06T11:14:44.076Z ถึง 2026-11-06T11:14:47.771Z** ก่อนหน้านี้เดิน UI เพื่อค้นหน้าต่างและรูปแบบ request จากเครือข่ายของ browser โดยไม่ได้อ่าน implementation
- reset เฉพาะ C3 สองครั้งในรอบสุดท้าย: ก่อนเริ่ม และก่อนจัดข้อมูล race เพื่อไม่ปะปนกับคำสั่งซื้อสองใบในกรณีโควตาสมาชิก ไม่ได้เลื่อนนาฬิกา รายละเอียดเวลาจริงอยู่ใน `c3/results.json`
- expected ราคาและขีดจำกัดถูกกำหนดในตารางด้านบนก่อนอ่านผล API ไม่แก้ expected ให้ตามผลจากหน้าเว็บ

## เบาะแสและประเด็นส่งต่อ

- หลังซื้อครบโควตา UI ยังเปิดผังและให้เลือกที่นั่งเพิ่มเติมได้ จากนั้นแจ้งปฏิเสธเมื่อยืนยัน นี่ไม่ขัดข้อกำหนดจำกัดจำนวน เพราะ server ปฏิเสธจริง แต่เป็นข้อเสนอปรับ UX ให้บอก “ใช้สิทธิ์ครบแล้ว” ก่อนผู้ใช้เลือก ไม่จัดเป็น defect P1
- การกู้ข้อมูล pending และการคืน quota หลัง refund ส่งต่อ C4/C5 ซึ่งเป็นเจ้าของ payment/refund lifecycle ไม่ทดลองคืนเงินซ้ำกับ charter เหล่านั้น
- C3 ตรวจเพียงการแข่งสองคำขอใน instance เดียว ไม่ถือเป็นผลทดสอบโหลดสูงหรือระบบหลาย instance
- ไม่รับรองนโยบายค่าธรรมเนียมหรือเวลารอของเว็บอ้างอิงภายนอก ค่าตัวอย่างเป็นกฎระบบจำลองของ ENCORE เท่านั้น
