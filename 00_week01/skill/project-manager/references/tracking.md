# ติดตามโครงการและจัดการสิ่งติดขัด

## Status report

ระบุวันที่รายงาน ช่วงข้อมูล baseline version และวันที่อัปเดตแหล่งข้อมูล
ใช้เกณฑ์ RAG ของโครงการก่อน หากไม่มีใช้เกณฑ์ด้านล่างและบอกว่าเป็นเกณฑ์ชั่วคราว

- **Green:** หลักฐานปัจจุบันรองรับว่าจะส่งมอบตาม commitment ได้ และไม่มี blocker สำคัญที่ยังไม่มีแผนรับมือ
- **Amber:** มีความเสี่ยงต่อ commitment แต่ยังมีทางแก้ที่เป็นไปได้ ระบุ owner และจุดตัดสินใจ
- **Red:** คาดว่าจะผิด commitment หรือมี blocker ที่แก้ภายในอำนาจทีมไม่ได้ ต้องตัดสินใจหรือปรับแผน
- **รอยืนยัน:** ข้อมูลไม่พอหรือเก่าเกินกว่าจะประเมิน ห้ามตีความว่าเป็น Green

สรุปสถานะรวมด้วยเหตุผล ไม่เฉลี่ยสีจนซ่อนปัญหาสำคัญ
ห้ามสร้างเปอร์เซ็นต์สำเร็จจากความรู้สึก ถ้ามีเพียงจำนวนงานที่เสร็จ ระบุว่าเป็นสัดส่วนตามจำนวนงาน
หากใช้ weighted progress ให้บอกน้ำหนัก ฐานคำนวณ และเกณฑ์ยืนยันว่าเสร็จ

รายงานควรมี:

1. สถานะรวมและผลต่อวันส่งมอบ/งบ/คุณภาพ พร้อมหลักฐาน
2. งานเสร็จรอบนี้ที่ตรวจรับหรือยืนยันได้
3. Milestone: baseline date / forecast date / actual date / ส่วนต่าง / เหตุผล
4. Blocker และความเสี่ยงหลัก: ผลกระทบ งานรับมือ owner และวันติดตาม
5. งานรอบถัดไปและสิ่งที่ต้องตัดสินใจ: ใครตอบ เรื่องอะไร ภายในวันใด ถ้าไม่ตอบกระทบอะไร

## RAID log

แยก Risk (อาจเกิด), Assumption (เชื่อไว้เพื่อวางแผน), Issue (เกิดแล้ว), Dependency (พึ่งสิ่งอื่น)
รักษา ID เดิมเมื่ออัปเดต และเชื่อม risk ที่เกิดแล้วเข้ากับ issue ใหม่เพื่อไม่ทำประวัติหาย

| ID | ประเภท | รายละเอียด / หลักฐาน | ผลกระทบ | Likelihood / impact | Owner | แผนรับมือ / trigger | วันต้องการ / ทบทวน | สถานะ |
|---|---|---|---|---|---|---|---|---|

Likelihood ใช้กับ Risk ไม่ใช้กับ Issue ที่เกิดแล้ว คะแนนเป็นเครื่องมือจัดลำดับ มิใช่ความน่าจะเป็นที่พิสูจน์แล้ว
Assumption ต้องมีวิธีตรวจและวันยืนยัน Dependency ต้องมีผู้ส่งมอบและเงื่อนไขรับงาน
การปิด Issue ต้องมีหลักฐาน ไม่ปิดเพียงเพราะถึง due date

## เมื่อโครงการล่าช้า

- หาสาเหตุจากข้อมูล เช่น requirement ยังไม่ยืนยัน, capacity ไม่พอ, test environment ไม่พร้อม หรือ vendor ส่งช้า
- ระบุงานและ milestone ปลายทางที่ได้รับผลจริง แยกเวลาที่เสียไปกับเวลาที่คาดว่าจะเสียเพิ่ม
- เสนอ recovery plan ที่มี owner, dependency, วันเริ่ม/จบ และสิ่งที่ต้องอนุมัติ
- ตรวจว่างานขนานทำได้จริงและไม่ตัดการทดสอบ/เกณฑ์ตรวจรับโดยไม่มีการตัดสินใจ
- แสดง forecast หลังแก้และ residual risk พร้อมเทียบ baseline เดิม

## จากบันทึกประชุม

แยก Decision / Action / Open question; action ต้องมี owner และ due date หากไม่ปรากฏให้รอยืนยัน
คำว่า “น่าจะได้” เป็น estimate หรือข้อเสนอ ไม่ใช่ commitment
อย่าอ้างว่า stakeholder อนุมัติจากการเงียบหรือเพียงเข้าประชุม
