# วางแผนส่งมอบและควบคุมการเปลี่ยนแปลง

## Project plan

ปรับความละเอียดตามขนาดโครงการ ใช้ข้อมูลเท่าที่มี ไม่ต้องบังคับใช้ Scrum ถ้าทีมทำงานแบบอื่น

1. เป้าหมายและตัวชี้วัดความสำเร็จ: แยก business outcome กับเกณฑ์ตรวจรับงาน
2. Scope in / scope out / constraint: อ้างข้อ TOR หรือ requirement ที่เกี่ยวข้อง
3. Deliverable และ acceptance: ระบุหลักฐาน ผู้ตรวจ ผู้มีอำนาจยอมรับ และเงื่อนไขก่อนส่งมอบ
4. WBS และกำหนดเวลา: ใช้ตารางด้านล่าง
5. Milestone: kickoff, requirement sign-off, พร้อมทดสอบ, UAT, go-live หรือขั้นที่ใช้จริง
6. Resource และการประสานงาน: owner, capacity ที่ยืนยันแล้ว, stakeholder, รอบรายงาน, escalation
7. งบและข้อจำกัด: แสดงเฉพาะข้อมูลที่มีหลักฐาน แยกงบอนุมัติ ค่าใช้จ่ายจริง และประมาณการ
8. RAID และคำถามเปิด: เรื่องที่อาจทำให้แผนใช้ไม่ได้และวันที่ต้องยืนยัน

| ID | Deliverable / งาน | อ้าง requirement | Owner / สถานะยืนยัน | Effort | Duration | เริ่ม | จบ | งานก่อนหน้า / เงื่อนไข | เกณฑ์เสร็จ |
|---|---|---|---|---|---|---|---|---|---|

Effort คือปริมาณแรงงาน เช่น person-days; duration คือระยะเวลาที่ผ่านไป ห้ามใช้แทนกัน
แผนที่มีแต่ deadline ยังไม่ใช่ประมาณการที่เป็นไปได้ ระบุ confidence ของ estimate และข้อมูลที่ยังขาด

## ตรวจความเป็นไปได้

- ระบุปฏิทินทำงาน ถ้ายังไม่มีใช้สมมติฐานจันทร์–ศุกร์และระบุว่ายังไม่หักวันหยุดองค์กร
- งานที่เริ่มได้หลังงานก่อนหน้าอนุมัติ ต้องสะท้อนเวลารออนุมัติ ไม่วางซ้อนโดยไม่มีเงื่อนไขรองรับ
- คนเดียวที่รับหลายงานต้องตรวจการชนของ capacity; การเพิ่มคนไม่ได้ทำให้งานทุกชนิดเร็วขึ้นเป็นสัดส่วนตรง
- หาก dependency และ duration ยังไม่ครบ ให้ระบุเส้นทางที่น่าจะกระทบวันส่งมอบ ไม่อ้างว่าเป็น critical path ที่คำนวณแล้ว
- หาก deadline เป็นไปไม่ได้ แสดงช่องว่างและทางเลือก: ลด scope, แบ่งส่งมอบ, เปลี่ยนลำดับ, เพิ่ม capacity ที่ทำได้จริง หรือเลื่อนวัน
  ใส่ผลกระทบด้านคุณภาพ ค่าใช้จ่าย และความเสี่ยงของแต่ละทางเลือก
- Buffer ต้องแสดงแยก ห้ามซ่อนด้วยการเลื่อน baseline

## Change request

| หัวข้อ | สิ่งที่ต้องระบุ |
|---|---|
| ID / ผู้ขอ / วันที่ | ระบุจากข้อมูลจริง ถ้าไม่มีใช้รอยืนยัน |
| เดิม → ใหม่ | ขอบเขตและเหตุผลของการเปลี่ยน |
| ผลกระทบ | deliverable, งานเพิ่ม/ลด, dependency, milestone, effort/cost, acceptance และความเสี่ยง |
| ทางเลือก | ไม่เปลี่ยน / ทำตามคำขอ / ทางเลือกที่ลดผลกระทบ |
| ข้อเสนอ PM | ทางเลือกที่แนะนำพร้อมเหตุผลและสมมติฐาน |
| การตัดสินใจ | ผู้มีอำนาจ สถานะ วันที่ และหลักฐานอนุมัติ |
| หลังอนุมัติ | baseline version ใหม่ งานที่ต้องอัปเดต ผู้รับผิดชอบ และผู้ต้องรับทราบ |

ก่อนอนุมัติให้ใช้สถานะ `เสนอเปลี่ยนแปลง` คง baseline เดิมและแสดง forecast แบบมีเงื่อนไข
ถ้าผู้ใช้มอบอำนาจอนุมัติและยืนยันการเปลี่ยนแล้ว ไม่ต้องถามซ้ำ บันทึกหลักฐานและปรับเฉพาะขอบเขตที่อนุมัติ
